# Implementation Plan: Cloudflare Edge Brain

**Branch**: `004-cloudflare-edge` | **Date**: 2026-07-11 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/004-cloudflare-edge/spec.md`

## Summary

Migrate the WhatsApp bot backend from Oracle VM (Node.js Express + WebSocket) to Cloudflare Workers + Durable Objects. The DO replaces the orchestrator as the WebSocket brain, the Worker replaces the Express API, and NeonDB replaces sql.js/SQLite. The Android phone becomes a pure actuator — no business logic, only sensors, actuators, and local timing.

**Why**: Oracle Ampere VMs are perpetually out of capacity. Cloudflare edge is always available, auto-heals from phone crashes, and has Chennai PoP ~10ms from Kerala.

## Technical Context

**Language/Version**: TypeScript 5.x (Cloudflare Workers runtime requires TypeScript or JavaScript ES modules)

**Primary Dependencies**: Cloudflare Workers SDK (`wrangler`), `@neondatabase/serverless` (PostgreSQL over HTTP), Cloudflare Durable Objects (WebSocket + SQLite storage), `itty-router` or Hono for Worker routing

**Storage**: NeonDB PostgreSQL (0.5 GB free tier) via `@neondatabase/serverless`, DO SQLite for orchestration state (1 GB free)

**Testing**: `wrangler dev --remote` for local DO/Worker testing, `vitest` with `miniflare` for unit tests

**Target Platform**: Cloudflare Workers (edge runtime), Android Termux (Node.js for phone-client), Vercel (React frontend)

**Project Type**: Distributed edge application — WebSocket server (DO) + REST API (Worker) + actuator client (phone) + SPA dashboard (Vercel)

**Performance Goals**: DO message processing < 500ms, Worker API latency < 100ms from Chennai edge, phone reconnect + resume < 60s

**Constraints**: No raw TCP sockets in Workers (must use HTTP-based DB driver), DO CPU timeout 30s per invocation, Free plan: 1M DO requests/month, 100K Worker requests/day, 1 GB DO SQLite

**Scale/Scope**: ~100-500 WhatsApp messages/day, ~1-5 phone calls/day, ~100 dashboard views/day

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Status | Notes |
|-----------|:------:|-------|
| **I. Simplicity First** | ⚠️ Needs justification | Introducing Cloudflare DO/Worker adds platform complexity vs single Node.js process. Justified: Oracle out of capacity blocks deployment, and auto-healing from phone crashes is a critical reliability gain. |
| **II. API-First Integration** | ✅ Pass | All endpoints maintain identical request/response contracts. Auth tokens in env vars. |
| **III. Config-Driven Behavior** | ✅ Pass | Templates remain in config module. Phone calibration coordinates in env/constants. |
| **IV. Observable & Auditable** | ✅ Pass | All events logged to NeonDB. DO errors surfaced via Worker health endpoint. |
| **V. Free-Tier-First Design** | ✅ Pass | Cloudflare Free plan, NeonDB Free tier, Vercel Hobby. All within free limits. |

**Violation justification**: Principle I (Simplicity) is violated by adding Cloudflare edge platform. The simpler alternative (Oracle VM) is blocked by "out of capacity" — we cannot deploy. Cloudflare edge also adds auto-healing (phone crash ≠ system death) which Oracle cannot provide without a second VM.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| New platform (Cloudflare Workers) | Oracle VM inaccessible due to capacity | 3 retry scripts tried; no guarantee of getting a slot |
| Distributed state (DO SQLite + NeonDB) | Hibernation destroys in-memory state | Single process on VM was simpler but VM not available |
| HTTP-based DB driver (no TCP) | Workers runtime limitation | Cannot use pg driver; must use @neondatabase/serverless |
